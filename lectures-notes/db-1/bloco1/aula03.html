O modelo relacional

O modelo relacional representa dados por relações (tabelas) identificadas por nomes distintos. Edgar F. Codd propôs o modelo em 1970; SQL tornou-se a linguagem predominante para criar, manipular e consultar bancos relacionais.

Relação
Estrutura tabular de dados.
Banco relacional
Coleção de relações com seus esquemas.

SGBD significa sistema de gerenciamento de banco de dados.

Nota-base · p. 1–2

Esquema e instância

Uma relação combina um esquema (definição dos campos) com uma instância (dados presentes em certo momento).

Alunos(id-aluno: string, nome: string,
       login: string, idade: integer, média: real)
  • Atributo: coluna; cada atributo tem um domínio, como inteiro ou texto.
  • Grau: número de atributos. Cardinalidade: número de tuplas da instância.
Nota-base · p. 2

Tuplas e tabela

Na instância abaixo, cada linha é uma tupla (registro); todas seguem os cinco campos definidos no esquema. No modelo relacional teórico, uma relação é um conjunto de tuplas: não contém linhas duplicadas.

id-alunonomeidademédia
50000Dave193,3
53666Jones183,4
53688Smith183,2

Exemplo didático — recorte da instância Alunos A1.

Sistemas comerciais podem ter comportamentos de duplicação que não refletem esse requisito teórico.

Nota-base · p. 2

Criar e modificar tabelas

SQL chama relações de tabelas. CREATE TABLE define o esquema; INSERT inclui linhas, DELETE remove linhas selecionadas e UPDATE altera valores.

CREATE TABLE Alunos (
  id_aluno CHAR(20), nome CHAR(30),
  idade INTEGER, media REAL
);
UPDATE Alunos
SET idade = idade + 1, media = media - 1
WHERE id_aluno = '53688';

Exemplo didático — SQL ilustrativa baseada na nota; tipos e detalhes de sintaxe variam entre SGBDs.

Nota-base · p. 3

Como avaliar um UPDATE

  1. WHERE determina quais linhas serão afetadas.
  2. SET calcula os novos valores; expressões usam o valor anterior da linha.
UPDATE Alunos
SET media = media - 0.1
WHERE media >= 3.3;

Exemplo didático — na instância da nota, 3,3 torna-se 3,2; 3,4 torna-se 3,3. A média 3,2 não satisfaz o filtro e não muda.

Nota-base · p. 3–4

Restrições de integridade

Uma restrição de integridade (RI) é uma condição sobre o esquema que limita quais instâncias são válidas. Restrições de domínio, chaves, referências e regras gerais protegem a consistência dos dados.

Esquema + restrições
→
SGBD verifica alterações
→
Aceita ou rejeita

Exemplo: impedir que dois alunos compartilhem o mesmo identificador.

Nota-base · p. 4

Superchaves e chaves

  • Superchave: atributo(s) cujo valor identifica univocamente uma tupla.
  • Chave candidata: superchave mínima; nenhum atributo pode ser retirado sem perder a unicidade.
  • Chave primária: chave candidata escolhida para identificar tuplas; não admite NULL.

Uma relação pode ter outras chaves candidatas além da chave primária.

Exemplo didático — em Alunos, id-aluno identifica a linha; a nota também ilustra nome + idade como outra combinação única.

Nota-base · p. 4

Declarar chaves em SQL

PRIMARY KEY declara a chave primária; UNIQUE restringe outra combinação para que não se repita. Uma restrição pode receber nome para facilitar a identificação de violações.

CREATE TABLE Alunos (
  id_aluno CHAR(20), nome CHAR(30), idade INTEGER,
  PRIMARY KEY (id_aluno),
  CONSTRAINT uq_nome_idade UNIQUE (nome, idade)
);

Exemplo didático — sintaxe SQL ilustrativa; o suporte a nomes, tipos e detalhes depende do SGBD.

Nota-base · p. 4

Chave estrangeira

Uma chave estrangeira (FK, foreign key) liga uma relação à chave candidata de outra relação. Cada valor não nulo da FK precisa encontrar correspondência na relação referenciada.

Matriculado
id-aluno (FK)
id-curso, nota
Alunos
id-aluno (PK)
nome, login…

Matriculado.id-aluno → Alunos.id-aluno

Exemplo didático — uma matrícula referencia o aluno existente.

Nota-base · p. 5

Manter referências válidas

Uma matrícula com id-aluno inexistente viola a integridade referencial. Apagar uma matrícula não invalida a tabela Alunos; apagar um aluno ainda referenciado pode invalidar Matriculado.

Ação referenciadaOpções usuais
Excluir/alterar alunoNO ACTION, CASCADE, SET DEFAULT, SET NULL

NO ACTION rejeita; CASCADE propaga; SET NULL só funciona se a coluna aceitar nulo e não violar outra restrição.

Exemplo didático — se id-aluno também integra a chave primária de Matriculado, não pode ser definido como NULL.

Nota-base · p. 5–7

Restrições gerais

Regras podem ir além de chaves e domínios básicos. Por exemplo, limitar a idade de alunos a valores maiores que 16 restringe os dados permitidos.

Restrição de tabela
Relacionada a uma tabela; avaliada quando ela muda.
Assertiva
Pode envolver várias tabelas; alterações em qualquer tabela envolvida podem exigir verificação.

Disponibilidade e sintaxe para restrições gerais variam entre SGBDs.

Nota-base · p. 5–6

Quando uma RI é violada

  • Inserir id-aluno duplicado ou nulo viola a chave primária.
  • Atualizar uma chave para valor já existente viola unicidade.
  • Inserir matrícula para aluno inexistente viola a FK.

Em geral, a instrução que introduz a violação é rejeitada. Para exclusões/atualizações referenciadas, escolha explicitamente a política adequada à regra do domínio.

Exemplo didático — os casos retomam Alunos e Matriculado da nota.

Nota-base · p. 6–7

Restrições e transações

Uma restrição pode ser verificada no fim de cada instrução ou, quando declarada e suportada como adiável, no commit (efetivação) da transação.

Início: referências temporariamente pendentes
→
Inserir linhas relacionadas
→
Commit valida consistência

Exemplo didático — Alunos referenciam Cursos e Cursos indicam um monitor Aluno; adiar a validação permite inserir primeiro as linhas mutuamente dependentes.

Nota-base · p. 7–8

Consultar: seleção

SELECT expressa quais colunas retornar; FROM indica a relação e WHERE filtra tuplas. O asterisco seleciona todas as colunas.

SELECT *
FROM Alunos A
WHERE A.idade < 18;

Exemplo didático — para a instância A1 da nota, o filtro retorna Madayan (11) e Guldu (12).

É um exemplo de seleção: restringe linhas sem alterar a tabela armazenada.

Nota-base · p. 8

Consultar: combinar relações

Uma junção relaciona tuplas por uma condição de correspondência. Aqui, o identificador do aluno associa Alunos à matrícula; o filtro mantém somente nota A.

SELECT A.nome, M.id_curso
FROM Alunos A, Matriculado M
WHERE A.id_aluno = M.id_aluno
  AND M.nota = 'A';

Exemplo didático — o resultado ilustrado na nota contém Smith e Topology112.

Forma SQL ilustrativa; a notação explícita de JOIN também é comum.

Relacionamento recursivo

Uma entidade pode se relacionar consigo mesma. Os papéis dão significado distinto às participações e orientam nomes de atributos e FKs.

Reporta_a(
  supervisor_cpf, subordinado_cpf,
  PK(supervisor_cpf, subordinado_cpf),
  FK supervisor_cpf → Funcionários(cpf),
  FK subordinado_cpf → Funcionários(cpf)
)

Exemplo didático — as duas referências apontam para Funcionários, mas representam papéis diferentes.

Cardinalidade e chave do relacionamento

Uma seta de restrição de chave no diagrama ER indica que, para cada ocorrência no lado oposto, há no máximo uma entidade associada naquele lado. A chave desse lado pode identificar a linha do relacionamento.

Funcionário
— Gerencia — →
Departamento (no máximo um gerente)

Assim, id-depto é chave de Gerencia(cpf, id-depto, desde). Alternativamente, os dados do gerente podem ser incorporados à tabela Departamento; campos opcionais podem ficar nulos.

Exemplo didático — mapeamento do relacionamento Gerencia.

Nota-base · p. 11–12

Participação total no ER

Participação total exige que toda entidade de um conjunto participe do relacionamento. Se cada departamento precisa de um gerente e pode ter no máximo um, incluir cpf não nulo em Departamento (com FK) expressa a regra localmente.

Já exigir que todo departamento apareça em Trabalha_em não se resolve com uma FK simples no sentido inverso: id-depto não é chave da relação Trabalha_em. Pode exigir assertiva ou mecanismo equivalente.

Exemplo didático — distinção entre a regra de Gerencia e a participação total em Trabalha_em.

Nota-base · p. 12–13

Mapear entidade fraca

Uma entidade fraca depende da chave da entidade proprietária e tem uma chave parcial própria. Sua chave relacional combina a chave parcial com a chave do proprietário.

Apólice_Dep(nomed, idade, custo, cpf)
PK: (nomed, cpf)
FK: cpf → Funcionários(cpf)
ON DELETE CASCADE

A chave composta identifica cada dependente e impede CPF nulo; excluir o proprietário pode remover seus dependentes associados.

Exemplo didático — Dependentes identificados por (nomed, cpf).

Nota-base · p. 15

Agregação no modelo ER

Agregação permite que um relacionamento participe de outro. No exemplo, Monitora relaciona Funcionários a uma ocorrência do relacionamento Financia entre Projetos e Departamentos.

Projetos — Financia — Departamentos
↑ agregado em Monitora
Funcionários — Monitora (até)

A tabela Monitora inclui a chave de Funcionários, as chaves de Financia e seu atributo descritivo. Financia só pode ser eliminada se não tiver atributos próprios e toda ocorrência aparecer em Monitora.

Visões: relações derivadas

Uma visão é uma tabela lógica derivada de uma consulta; suas linhas não precisam ser armazenadas como as de uma tabela base. Ela pode ser consultada como uma relação.

CREATE VIEW Estudantes_B AS
SELECT A.nome, A.id_aluno, M.id_curso
FROM Alunos A, Matriculado M
WHERE A.id_aluno = M.id_aluno
  AND M.nota = 'B';

Exemplo didático — estudantes e cursos em que obtiveram B.

Nota-base · p. 16

Visões: abstração e acesso

  • Independência lógica: uma visão pode oferecer uma interface externa estável mesmo quando a organização conceitual muda.
  • Segurança: conceda acesso à visão com apenas as colunas apropriadas, em vez de expor toda a tabela base.
Tabela base Alunos (inclui média)
→
Visão autorizada (nome, idade)
→
Usuário

Exemplo didático — a visão pode ocultar a média dos alunos.

Nota-base · p. 16

Atualizar uma visão

Uma atualização em visão é mais simples quando sua origem é uma única tabela-base, com seleção e projeção, sem agregação: a alteração pode ser traduzida sem ambiguidade.

CREATE VIEW Estudantes_Bons AS
SELECT id_aluno, media
FROM Alunos
WHERE media > 3.0;

WITH CHECK OPTION impede inserir ou atualizar pela visão uma linha que, após a alteração, não satisfaz seu filtro.

Exemplo didático — sem essa opção, inserir média 2,8 poderia alterar a tabela base sem a linha aparecer na visão.

Nota-base · p. 17

Por que restringir atualizações

Uma visão que combina Alunos e Clubes pode conter a linha Smith–Hiking. Excluí-la da visão deixa duas alterações possíveis na base:

  • Excluir Smith de Alunos — remove também outras linhas associadas a Smith.
  • Excluir só sua associação Hiking de Clubes.

Como a intenção não é determinada univocamente pela linha da visão, permitir a operação poderia causar efeitos colaterais. Algumas atualizações devem ser proibidas.

Exemplo didático — ambiguidade de exclusão na visão EstudantesAtivos.

Nota-base · p. 17–18

Alterar ou remover objetos

  • DROP TABLE remove tabela e definição; RESTRICT impede a remoção se objetos dependem dela.
  • CASCADE também remove objetos dependentes; use com cautela.
  • DROP VIEW remove uma visão.
  • ALTER TABLE muda a estrutura, por exemplo adicionando coluna.
ALTER TABLE Alunos
ADD COLUMN nome_familia CHAR(10);

Na nota, linhas existentes recebem NULL na coluna nova; restrições e regras do SGBD podem afetar a operação.

Nota-base · p. 18–19

Atividade: matrícula consistente

Exemplo didático — Alunos(id_aluno) é referenciada por Matriculado(id_aluno).

  1. Alunos não contém 99999. A matrícula com id_aluno 99999 pode ser inserida?
  2. O aluno 53688 tem matrícula. O que ocorre ao excluí-lo sob NO ACTION? E sob CASCADE?
  3. Se id_aluno participa da chave primária de Matriculado, pode receber NULL?
Ver resposta

1. Não: a FK ficaria sem correspondência. 2. NO ACTION rejeita a exclusão enquanto houver referência; CASCADE remove as matrículas dependentes. 3. Não: componentes da chave primária não podem ser NULL. Escolha a ação referencial de acordo com a regra de negócio.

Nota-base · p. 5–7

Resumo

  • Relações têm esquema e instância; tuplas respeitam atributos, domínios e unicidade teórica.
  • Chaves e restrições de integridade controlam identidade e referências.
  • Consultas selecionam e combinam dados; mapeamentos ER levam entidades, relacionamentos e dependências a tabelas.
  • Visões oferecem interfaces derivadas, úteis para abstração e segurança; atualizações podem ser restritas quando ambíguas.
  • Transações e comandos DDL completam a gestão da consistência e do esquema.
