Aula 02

Processos, Threads e Multiprogramação

Prof. Paulo Rettore

Universidade Federal de Lavras

Sistemas Operacionais

Objetivos de aprendizagem

Ao final, você deverá ser capaz de:

  • distinguir processo, thread, multiprogramação e tempo compartilhado;
  • identificar o que é privado e o que é compartilhado entre threads;
  • comparar os modelos N:1, 1:1 e N:M;
  • reconhecer as principais operações POSIX e equivalentes de Linux/Windows;
  • explicar por que concorrência exige coordenação e pode afetar responsividade e desempenho.

O foco é entender as abstrações e os mecanismos, não memorizar uma API isolada.

Nota-base · p. 1–5

Multiprogramação e tempo compartilhado

Multiprogramação

Vários processos permanecem na memória. O sistema alterna o uso da CPU entre eles, aproveitando melhor o processador quando um processo aguarda E/S.

Tempo compartilhado

É uma extensão interativa: o escalonamento alterna tarefas com rapidez suficiente para que vários usuários ou programas tenham a impressão de usar a máquina simultaneamente.

Ideia-chave: concorrência é a composição dos avanços das tarefas; paralelismo é execução simultânea em mais de um núcleo.

Nota-base · p. 1–2

O que compõe um processo

  • Texto: instruções do programa.
  • Contador de programa: próxima instrução.
  • Registradores: estado do processador.
  • Pilha (stack): parâmetros, retornos e variáveis locais.
  • Dados: variáveis globais.
  • Heap: memória alocada dinamicamente.
  • Espaço virtual: visão de memória própria e protegida.

Processo não é apenas o arquivo executável: é o programa junto de seu estado e dos recursos necessários para executar.

Nota-base · p. 2

O que é uma thread

Uma thread (fluxo de execução) é a unidade básica de utilização da CPU. Ela possui:

ID
identifica o fluxo
Estado próprio
contador de programa e registradores
Pilha
chamadas e variáveis locais

Threads do mesmo processo compartilham código, dados, arquivos abertos e sinais. Por isso, comunicam-se diretamente pela memória, mas também precisam de sincronização.

Nota-base · p. 2

Exemplo: servidor responsivo

Imagine um servidor que recebe uma requisição e precisa ler um arquivo.

1. Thread recebe a requisição
2. A leitura bloqueia ou espera E/S
3. Outra thread pode atender outro cliente
4. A primeira retoma quando os dados chegam

Multithreading pode melhorar a responsividade e o aproveitamento do hardware, especialmente em sistemas multiprocessadores. O ganho não é automático: trabalho compartilhado requer sincronização.

Nota-base · p. 1–2

Modelos de threads: como usuário chega ao núcleo

Threads de nível de usuário são gerenciadas por uma biblioteca da aplicação; threads de nível de núcleo são gerenciadas pelo sistema operacional. O modelo descreve o mapeamento entre ambas.

N:1
muitas → uma
1:1
uma → uma
N:M
muitas → várias

O mapeamento influencia bloqueio, paralelismo, custo de criação e complexidade da implementação.

Nota-base · p. 2–3

Modelo Muitos-para-Um (N:1)

Funcionamento

Várias threads de usuário são mapeadas para uma única thread de núcleo. A biblioteca gerencia a troca no espaço do usuário, sem exigir uma chamada de sistema a cada troca.

Limitações

  • uma chamada bloqueante pode bloquear todo o processo;
  • não explora paralelismo em múltiplos processadores;
  • apenas uma thread chega ao núcleo por vez.
Vantagem: gerenciamento rápido e eficiente no espaço do usuário.
Nota-base · p. 2

Modelo Um-para-Um (1:1)

Cada thread de usuário corresponde a uma thread de núcleo. Assim, o núcleo pode escalonar threads individualmente.

Bloqueio isolado
uma thread bloqueada não precisa parar as demais.
Paralelismo
threads podem executar em processadores diferentes.
Custo
muitas threads implicam mais estruturas e trabalho no núcleo.

A nota identifica Linux e versões mais recentes do Windows como sistemas que adotam predominantemente este modelo. A formulação é contextual à implementação descrita na fonte.

Nota-base · p. 2–3

Modelo Muitos-para-Muitos (N:M)

Muitas threads de usuário são multiplexadas sobre um número menor ou igual de threads de núcleo.

  • permite criar muitas threads de usuário sem uma thread de núcleo para cada uma;
  • possibilita execução paralela quando há múltiplas threads de núcleo;
  • uma thread bloqueada pode liberar o núcleo para outra;
  • combina flexibilidade com paralelismo, mas é mais complexo de implementar.

Comparação: N:1 simplifica e limita; 1:1 expõe paralelismo e custa mais; N:M tenta equilibrar os dois.

Nota-base · p. 3

POSIX e o gerenciamento de execução

POSIX (Portable Operating System Interface) define uma interface padrão para sistemas operacionais do tipo Unix. A nota usa POSIX para organizar operações de processos e a API Pthreads para threads.

Processo

criação, substituição da imagem, espera, término e identificação.

Thread

criação, espera por outra thread, término, identificação, cancelamento e sincronização.

Uma API descreve como solicitar operações; o escalonamento e os recursos continuam sob controle do sistema operacional.

Nota-base · p. 3

Operações POSIX para processos

  • fork(): cria um filho; retorna o ID do filho ao pai, 0 ao filho e -1 em caso de erro.
  • exec() e família: substituem a imagem do processo por outro programa; em sucesso, não retornam.
  • wait()/waitpid(): permitem ao pai esperar pelo término de filho(s).
  • exit(): termina e devolve status ao pai.
  • getpid()/getppid(): obtêm os IDs do processo e do pai.
fork: pai cria filho
exec: uma imagem pode ser substituída
waitpid: pai coordena término
Nota-base · p. 3

Operações Pthreads para threads

  • pthread_create(): cria uma thread e define a função que ela executará.
  • pthread_join(): bloqueia a chamadora até a thread indicada terminar.
  • pthread_exit(): termina a thread e pode fornecer um valor de retorno.
  • pthread_self(): obtém o ID da thread chamadora.
  • pthread_cancel(): solicita o cancelamento de outra thread.

Sincronização faz parte do Pthreads: mutexes e variáveis de condição incluem operações como pthread_mutex_lock() e pthread_cond_wait().

Nota-base · p. 3–4

Atividade 1 — escolha do modelo

Um processo possui várias threads de usuário. Em uma arquitetura com vários processadores, uma delas faz uma chamada bloqueante, enquanto as demais poderiam continuar. Compare N:1 e 1:1: qual modelo permite melhor continuidade e por quê?

Ver resposta

No N:1, a chamada bloqueante da única thread de núcleo bloqueia o processo inteiro e não há paralelismo. No 1:1, cada thread de usuário tem uma thread de núcleo; outra pode ser escalonada e, em multiprocessador, executar em paralelo.

Nota-base · p. 2–3

Processos e threads no Linux

A nota descreve o Linux como tratando processos e threads de forma integrada: uma thread pode ser vista como um tipo especial de processo que compartilha certos recursos. clone() permite controlar quais recursos pai e filho compartilharão.

  • task_struct representa cada tarefa no kernel;
  • fork() cria um novo processo duplicando a estrutura do pai;
  • exec() carrega outro programa na imagem do processo;
  • a NPTL (Native POSIX Thread Library) implementa Pthreads e usa o modelo 1:1, conforme a nota.

Detalhes internos de kernel podem variar por versão; aqui são apresentados no contexto da fonte da aula.

Nota-base · p. 4

Processos e threads no Windows

No Windows, processos e threads são objetos distintos gerenciados pelo kernel.

Processo

Contêiner com espaço virtual privado, token de acesso e pelo menos uma thread. A criação usa CreateProcess(); o processo precisa de threads para executar código.

Thread

Cada processo começa com uma thread primária e pode criar outras com CreateThread() ou _beginthreadex em C/C++. O kernel escalona threads individualmente.

O Windows oferece primitivas de sincronização para coordenar threads.

Nota-base · p. 4–5

Atividade 2 — raciocínio sobre concorrência

Duas threads incrementam uma variável global compartilhada. Cada incremento é lido como: ler valor, somar 1, gravar valor. Se ambas leem o mesmo valor antes de gravar, o que pode ocorrer? Qual mecanismo deve ser considerado?

Ver resposta

Pode ocorrer uma condição de corrida: uma gravação sobrescreve a outra e o resultado fica menor que o número de incrementos esperado. O acesso precisa ser coordenado, por exemplo com um mutex; a nota cita mutexes e operações de lock/unlock como mecanismos Pthreads.

Síntese: decisões e consequências

Processo

programa em execução, com espaço de endereçamento e recursos próprios.

Thread

fluxo leve de execução, compartilhando recursos do processo.

SO

cria, escalona, sincroniza e termina essas entidades.

  • Multiprogramação mantém trabalhos disponíveis e alterna CPU.
  • Tempo compartilhado acrescenta interatividade para usuários concorrentes.
  • O modelo de threads afeta bloqueio, paralelismo, custo e complexidade.
  • Linux e Windows modernos usam predominantemente 1:1, mas suas APIs de criação diferem.
